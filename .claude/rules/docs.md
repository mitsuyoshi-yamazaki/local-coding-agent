# docs/ の書き方

docs/ の説明の文書を書くときの規則である。受け渡しのファイル（`docs/inbox/`・`docs/outbox/`）と、進行の記録（`docs/progress.md`）には当てない。docs/ の下に新しいディレクトリを作ったら、上の `paths` に足す。

`docs/requirements.md` は、上流の要件を写したものである。上流から届いた要件の意味を変えずに置き、下の「静的な情報だけを書く」は当てない。

## 読み手

- 想定読者は、コーディングエージェントの仕組みを知らないソフトウェアエンジニアである
- 用語は、初めて出たところで意味を書く

## 静的な情報だけを書く

- リポジトリが公開された状態を書く
- 経緯を書かない。例: いつ何を足したか・これから何をするか・まだ入っていない・使い始めるときに足していく・取り込むときに確かめる
- 決まっていないことは書かない（「後で決める」とも書かない）
- 「どう作り、どうなったか」（経緯・結果・数値）は outbox の記録に書く。docs/ に書くのは「どういう仕組みか」である

## 出典

- 記述には出典（公式の文書・リポジトリ）と、確かめた日を付ける
- このリポジトリで実測したことは「実測」と書く

## docs/technologies/

- 一般的なソフトウェアエンジニアが知っていることは書かない（例: HTTP の API とは何か・curl での呼び方）
- その技術に固有のことと、このリポジトリでの使い方だけを、短く書く。例: 「「API で呼ぶ」とはどういうことか」を説明せず、「Ollama はローカルのサーバとして動く。ollama.com のサービスも同じ API で使える」と書く
- 技術の文書を足したら、`docs/technologies/README.md` の一覧に足す

## docs/features/

- 機能ごとに、ディレクトリ `docs/features/f-NN-<機能名>/` を作る。`NN` は `docs/features.md` の番号（2桁。名前の順に並べると機能の順になる）。`<機能名>` は英小文字とハイフン
- 中に置くもの:
  - `spec.md`: 実装前の仕様（人が承認したもの）
  - `implementation.md`: 実装した後の、実際に実装された仕様と仕組み
  - `measurements.md`: 計測の結果（あれば）
  - `handoff.md`: セッションの間の引き継ぎ（下）
  - `memo.md`: 持ち主のメモ。git に入れない（`.gitignore`）。main 側が機能の branch を取り込むときに、空のファイルとして作る（skill `merge-feature`）。中身は持ち主が書く
  - そのほか、その機能に関わる文書
- `spec.md` は実装の前の仕様、`measurements.md` は計測した時点の結果として残す。この2つには、上の「経緯を書かない」を当てない。実装で仕様が変わったら、`spec.md` は直さず、`implementation.md` に書く

### handoff.md

- 機能を実装したセッション（worktree 側）が、人の問いに答えるセッション（main 側）と、さらに後のセッションに引き継ぐためのファイルである。人が読む想定ではないので、大きくてよい。上の「読み手」と「静的な情報だけを書く」を当てない
- commit するので公開される。個人の情報・秘匿情報・手元の絶対パスを書かない
- 実装したセッションが書く中身:
  - 進み具合（どの段まで済んだか・branch・最後の commit）
  - 仕様を決めるときに人と話したこと
  - 実装の全体像（ファイルごとの役目・データの流れ）
  - 設計の選択と理由・捨てた案
  - 実装前の仕様との違い
  - テストで確かめたこと・確かめていないこと
  - 人が問いそうなことと答え
  - 分かっている問題・残したこと
  - main と衝突しそうな所（main で確認中の機能と同じファイルを触った所）
- main 側のセッションは、来た問いと答え・直したことを「問いと答えの記録」の節に足す。後のセッションが、どのような問いが来たかを引き継げるようにする

## 読む順

- 文書を足したら、`docs/README.md` の読む順に足す
