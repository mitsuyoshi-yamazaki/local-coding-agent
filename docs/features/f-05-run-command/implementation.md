# F-05 コマンドの実行と、結果を読んで直すループ: 実装した仕様と仕組み

[実装前の仕様](spec.md) に対して、実際に実装した仕様と、その仕組みである。

## 使い方

起動は F-03 と同じである。モデルが `run_command` を呼ぶと、呼び出しの1行の後に走らせるコマンドが出て、実行してよいかを問われる。結果の1行には、終了コードと、モデルに返した結果の行数が出る。

```text
> テストを走らせて、通らないものを直せ
…
[道具] run_command {"command": "python3 -m unittest"}
$ python3 -m unittest
実行してよいか [y/N]: y
→ 終了コード: 1・44 行
…
[道具] edit_file {"path": "duration.py", …}
…
[道具] run_command {"command": "python3 -m unittest"}
$ python3 -m unittest
実行してよいか [y/N]: y
→ 終了コード: 0・6 行
```

- `y` か `yes` で走らせる。それ以外の答えと Ctrl-D では走らせず、`利用者が実行を拒んだ` をモデルに返す
- 時間切れのときは `→ 時間切れ: 120 秒で止めた・<行数> 行` になる
- `command` が空のときなど、走らせられないと分かったときは、問わずに `→ 誤り: …` を出してモデルに返す
- **Ctrl-C**: コマンドの途中で押すと、コマンドと、コマンドが起こしたプロセスを止め、その回を止める（F-04 の止めた回の扱い）

## 仕組み

### 道具 run_command

`tools/run_command.py` の道具である。変更を伴う道具（`changes` が真）なので、実行の前に人に確かめる。走らせてよいコマンドの規則は無く、全てのコマンドを問う。

| 入力 | 型 | 意味 |
|---|---|---|
| `command` | 文字列。必須 | 走らせるコマンド |
| `timeout` | 整数。1 以上 600 以下 | 終わるのを待つ秒数。過ぎたら止める。既定は 120 |

結果の文は、1行目が終了コードか時間切れ、2行目からがコマンドの出力である。

```text
終了コード: 1
FFFFFF.
======================================================================
FAIL: test_cases (test_duration.FormatDurationTest.test_cases) (seconds=90)
…
FAILED (failures=6)
```

```text
時間切れ: 2 秒で止めた
test_empty (test_words.SplitWordsTest.test_empty) ... ok
test_one_word (test_words.SplitWordsTest.test_one_word) ... ok
test_words_and_spaces (test_words.SplitWordsTest.test_words_and_spaces) ...
```

（2つ目は、`words` の写しで `python3 -m unittest -v` を `timeout` 2 で走らせた結果。実測。止まったテストの名前が最後に出ている）

- 出力の末尾の改行は除く。出力が無ければ `（出力なし）`
- 終了コードが 0 でないときも、時間切れのときも、誤りの結果（`is_error`）にしない。テストの失敗は、モデルが求めた情報であって、道具の失敗ではないためである
- 出力が 10,000 字を超えたら、先頭の 5,000 字と末尾の 5,000 字を残し、間に `（中略: <省いた字数> 字。全体は <全体の字数> 字）` の1行を挟む。行の途中でも切る
- 終了コードは、シェル（`/bin/sh`）の終了コードである。シェルが信号で止まったときは、負の数（`-9` なら SIGKILL）になる
- 誤り（`is_error`）: `command が空である`（空白と改行だけも空とする）・`command に NUL の字がある`・`走らせられない: <理由>（作業ディレクトリ: <パス>）`

下見（`preview`）は `$ <コマンド>` である。呼び出しの1行（`[道具] run_command {…}`）は入力を JSON で出すので、複数の行のコマンドは `\n` で1行に出る。下見は、コマンドをそのまま出す。

Claude Code の Bash は、時間切れの既定が 2 分、モデルが選べる上限が 10 分で、出力は 30,000 字まで結果に入れる。コマンドの中の `cd` は次のコマンドに残り、環境変数は残らない（出典）。

### プロセスの走らせ方

`tools/process.py` の `run_shell` が、Python の `subprocess.Popen` でコマンドを走らせる。

| 点 | 走らせ方 |
|---|---|
| シェル | `/bin/sh -c <command>`。パイプ（`|`）や `&&` を、そのまま書ける |
| 作業ディレクトリ | 毎回、エージェントを起動したディレクトリ。コマンドの中の `cd` は、そのシェルが終われば消える |
| 環境変数 | エージェントの環境変数を、そのまま渡す。コマンドの中で設定したものは、そのシェルが終われば消える |
| 標準入力 | `/dev/null`。入力を待つコマンドは、入力の終わりを受けて進む |
| 標準出力と標準エラー | 1つのパイプにまとめる（`stderr=STDOUT`）。端末で見るときと同じ順で混ざる。UTF-8 として読み、読めないバイトは `�`（U+FFFD）に置き換える |
| プロセスのグループ | 子のプロセスを、新しいセッションで始める（`start_new_session=True`。子のプロセスで `setsid()` が呼ばれる）。子のプロセスは、新しいプロセスのグループの頭になり、グループの番号は子のプロセスの番号と同じになる。シェルが起こしたプロセスも、同じグループに入る |

グループに分けるのは、シェルだけでなく、シェルが起こしたプロセスまで、まとめて止めるためである。シェルだけを止めると、シェルが起こしたプロセス（`python3 -m unittest` や、`&` で後ろに回したもの）は残る。残ったプロセスが出力のパイプを握っていると、出力の終わりが来ないので、エージェントはいつまでも待つ。

止めるときは、グループの全てに SIGKILL を送る（`os.killpg`）。送るのは次のときである。

| とき | 送った後 |
|---|---|
| 時間切れ（`communicate` が `TimeoutExpired` を投げた） | `communicate` を呼び直して、止めるまでの出力を読み切る（呼び直しても出力は失われない）。出力の終わりは 1 秒まで待ち、来なければ、そこまでの出力を返す。終了コードは無し（時間切れ） |
| Ctrl-C（`communicate` の途中で `KeyboardInterrupt`） | 子のプロセスを待ってから、`KeyboardInterrupt` を投げ直す。ループは、その呼び出しに `利用者が止めた` の結果を入れる（F-04） |
| コマンドが終わった | シェルが後ろに回して、出力のパイプを手放したプロセス（`server > log &` など）が残っていれば止める。残っていなければ、何もしない |

端末で Ctrl-C を押すと、端末は、手前のプロセスのグループ（エージェント）に SIGINT を送る。子のプロセスは別のセッションにいるので、SIGINT を受けない。止めるのはエージェントである。子のプロセスは端末も持たないので、端末から入力を読もうとするコマンド（パスワードを問うものなど）は、読めずに誤りで終わる。

後ろに回したプロセスが出力のパイプを握ったまま走り続けると（`sleep 100 &` など）、出力の終わりが来ないので、時間切れまで待ち、`時間切れ` の結果になる。

`setsid` などで別のセッションに移ったプロセスは、グループの外なので止められず、走り続ける。それが出力のパイプを握っていると、グループを止めても出力の終わりが来ない。そのため、止めた後に出力の終わりを待つのは 1 秒までにして、来なければ、そこまでの出力を返す（パイプは、エージェントの側で閉じる）。

### 結果の1行

道具の形（`tools/tool.py` の `Tool`）に、結果の文から画面の結果の1行を作る関数（`summary`）を足した。`loop/tool_call.py` の `result_summary` は、次の順で結果の1行を作る。

| 結果 | 1行 |
|---|---|
| 誤りの結果 | `誤り: <結果の文>`（F-03 と同じ） |
| 道具が `summary` を持つ | `summary` が返した文。`run_command` は、結果の文の1行目と行数（`終了コード: 1・44 行`） |
| それ以外 | `<行数> 行`（F-03 と同じ） |

### 入力の照らし

`tools/input_check.py` に、数の上限（JSON Schema の `maximum`）を足した。下限（`minimum`）と同じく、真偽値は数としない。`timeout` に 601 を渡すと、実行せずに `入力が定義に合わない: timeout は 600 以下でなければならない（受けた値: 601）` を返す。

### system prompt

`context/system_prompt.py` の既定の指示を、次のように直した。

| 節 | 直したこと |
|---|---|
| できること | 「コマンドを走らせる道具は持たない」を除き、`run_command` を持ち、実行の前に利用者がコマンドを見て確かめる、を足した。「拒まれたら、やり方を変えるか、利用者に尋ねる」を、全ての変更を伴う道具に掛かる1項にした |
| 道具の使い方 | コードを直したら `run_command` でテストを走らせて確かめる。失敗したら出力を読んで直し、もう一度走らせる。通ったことを確かめてから答える・テストの走らせ方が分からなければ README などを読む・毎回作業ディレクトリで走り、`cd` と環境変数は残らない・標準入力は空なので、入力を待つコマンドと終わらないコマンドは走らせない |
| ハーネスが入れる情報 | `run_command` の結果の1行目は、終了コード（0 なら成功）か時間切れで、2行目からがコマンドの出力 |

### 走行の記録

欄は F-04 と同じである（[F-03 の欄](../f-03-tool-loop/implementation.md#走行の記録)と [F-04 の `preview`](../f-04-file-edit/implementation.md#走行の記録)）。`run_command` の道具の件では、次のようになる。

| 欄 | 中身 |
|---|---|
| `input` | `command` と、渡されていれば `timeout` |
| `preview` | `$ <コマンド>` |
| `result` | モデルに返した結果の文。1行目の `終了コード: <N>` か `時間切れ: <秒> 秒で止めた` で、通ったかを分けられる |
| `seconds` | コマンドを走らせていた時間 |

結果に入れなかった出力（10,000 字を超えて省いた所）は、どこにも残らない。

## 試すための材料

`tasks/f-05-run-command/` に、通らないテストを持つ小さなプロジェクトを2つ置く。写し方と判定のコマンドは `tasks/f-05-run-command/README.md` にある。写しを作業ディレクトリにして起動し（モデルがリポジトリの中の答えを読まないため）、試すたびに写し直す。どちらのプロジェクトにも、テストの走らせ方（`python3 -m unittest`）を書いた `README.md` がある。

| プロジェクト | 中身 | 誤り | テストを走らせると |
|---|---|---|---|
| `duration/` | 時間の長さの文字列と秒数を変換する `parse_duration`（`"1h30m"` → 5400）と `format_duration`（5400 → `"1h30m"`） | `parse_duration` は数を足した後に、読んだ数字を空に戻さない。`format_duration` は、残りの秒数を単位の秒数ではなく 60 で割った余りにしている | 6件が失敗する。`AssertionError: 11400 != 5400`・`'1h' != '1h30m'` など、期待した値と実際の値が出る |
| `words/` | 文をスペースで語に分ける `split_words` | 次に探し始める位置を、スペースの次ではなくスペースの位置にしている | スペースのある文のテストで、ループが終わらない。`run_command` では時間切れになる |

| 依頼の例 | 判定 | 見ること |
|---|---|---|
| `テストを走らせて、通らないものを直せ`（`duration`） | `judge.py` で、写しのテストが通る | テストの走らせ方を README で確かめるか。失敗の出力から直す所を見つけるか。直した後に走らせ直すか。通ったことを確かめてから終えるか |
| 同じ（`words`） | 同じ | 時間切れの結果を読んで、終わらない所を見つけるか。`timeout` を短くする・`-v` で止まったテストを見るか |

判定の `judge.py` は、写しのテストを `unittest` で走らせ、30 秒で打ち切る。通れば終了コード 0、通らない・終わらなければ 1 を返す。直っていない `words` でも、判定は止まらない。

ほかに、問いで拒んだときと、コマンドの途中で Ctrl-C を押したときに、モデルがどうするかを見る。

道具を写しに直に掛けて、次を確かめた（実測。モデルは使っていない）。

- 写したばかりの状態では、どちらの判定も通らない（`duration` は6件が失敗、`words` は 30 秒で打ち切られる）
- `duration.py` の2か所（数字を空に戻す1行を足す・`rest % 60` を `rest % size` にする）を `edit_file` で直すと、`run_command` の結果は `終了コード: 1`（1か所目の後）から `終了コード: 0`（2か所目の後）になる
- `words.py` の `start = end` を `start = end + 1` にすると、テストが通る

## 実装前の仕様との違い

仕様の振る舞いは変えていない。仕様に書いていなかった細部は次のとおり。

| 点 | 実装 |
|---|---|
| 止め方 | グループの全てに SIGKILL を送る（SIGTERM を送って待つことはしない） |
| 出力の末尾 | 末尾の改行を除いてから、字数を数え、`（出力なし）` かを決める |
| 切り詰め | 行の途中でも切る |
| 空の `command` | 空白と改行だけのものも、空とする |
| 終了コード | シェルが信号で止まったときは、負の数になる |
| 後ろに回したプロセス | 出力のパイプを握ったまま走り続けると、時間切れまで待つ |
| グループの外に出たプロセス | 止められない。止めた後に出力の終わりを待つのは 1 秒まで |
| 結果の1行 | 道具の形に `summary` を足し、`run_command` だけが持つ |
