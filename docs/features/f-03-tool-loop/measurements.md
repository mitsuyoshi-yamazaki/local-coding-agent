## 読み取れること

- **ループは回り、答えは3つの問いとも正しかった**。モデルを呼んだ回数は、1. が4回、2. が3回、3. が4回。どの呼び出しにも、Ollama が `id`（`call_m5b41k1a` の形）を付けて返したので、ハーネスが付ける `call_<回>_<歩み>_<順>` は使われなかった
- **`offset` で続きを読んだ**。読み残しの知らせの文を読み、渡す値をそのまま使った
- **文脈の長さ（4096）を超えた入力も、切り詰められなかった**。2. の2歩目と3歩目の入力（23927・28811 トークン）は、文脈の長さの6〜7倍だった。それでも、`prompt_eval_count` は会話の全体の数で、モデルは先頭の依頼に、末尾の結果から答えた。Ollama は、形式が safetensors のモデル（MLX の実行系で動くもの）では、文脈の長さを超えた発言を落とさない（ソースの `ChatHandler`。下の出典）。MLX の実行系の中で 4096 がどう使われるかは確かめていない
- **大きな道具の結果は、次の歩みの入力の処理の時間にそのまま出る**。2. の1回目の結果（2002 行・36038 字）は約 2.3 万トークンで、2歩目の入力の処理に 299 秒かかった。道具の実行は 0.01 秒で、時間のほぼ全てはモデルが結果を読む時間である
- **歩みをまたいで、前の要求の部分を処理し直していない**。2. の3歩目は、入力 28811 トークンを 71.11 秒で処理した。全てを処理したなら 405 トークン/秒になり、ほかの回の速さ（69〜91）を大きく超える。増えた 4884 トークンだけなら 69 トークン/秒で、合う。1. と 3. の2歩目以降も、入力の処理は 0.7〜1.4 秒だった
- **入力が長いほど、1トークンあたりの処理が遅くなる**。増えた分の処理の速さは、2. の1歩目（957 トークン）91・2歩目（22970 トークン増）77・3歩目（4884 トークン増、全体 28811）69 トークン/秒だった。出力の速さも 13.2 から 8.9 トークン/秒に落ちた。前のトークンが多いほど、通常の注意（attention）の層の計算が増えるため、と考えると合う（推定）
- **1歩目の入力は約 950 トークン**。F-02 の既定の指示での1回目（「今何時？」で 315 トークン）より約 630 トークン多い。道具の定義2つと、既定の指示に足した「道具の使い方」の節が入るためである（内訳は測っていない）。2歩目以降が数秒で返るのに対し、1歩目は入力の処理だけで 10〜13 秒かかる
- **誤りの結果を読んで、やり方を変えた**。3. では、無いことを確かめるためにディレクトリを見てから、要約できないと答えた
- **止めた回は、次の回に入らない**。止めた後の依頼で前の問いを聞くと、モデルは「履歴がありません」と答えた。読み終えた道具の結果も捨てられる
- **別のセッションの1歩目で、使い回したり、しなかったりした**。どの1歩目も、system prompt・道具の定義・送った時刻の途中までが前のセッションと同じ文だった。モデルがメモリに載っていた2回の1歩目のうち、3. の1歩目（前のセッションは 2. で、最後の入力 28811 トークン）は 13.02 秒かかり、4. の1歩目（前のセッションは 3. で、最後の入力 1124 トークン）は 3.02 秒で済んだ。F-02 では、分かれ目が前の要求の終わりより手前だと処理し直す、と推定したが、4. の1歩目は分かれ目が前の要求の終わりより手前でも使い回したと考えられ、その推定だけでは説明できない。理由は確かめていない
