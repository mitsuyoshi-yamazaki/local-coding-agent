# 要件

このリポジトリの要件の全てである。正本は上流のリポジトリ（非公開）にあり、変更は `docs/inbox/` で届く。

CLAUDE.md と Claude Code の設定は、この要件から書き起こしている。要件と設定の対応は [Claude Code の設定](claude-code-settings.md) にある。

## 目的

- ローカル LLM を使い、Claude Code の主要機能を自分で実装することで、仕組みを理解する
- 作ったエージェントを日常の道具として使い続けることは目的にしない

## 作るもの

- ローカル LLM で動くコーディングエージェント。作る機能と順序は [作る機能](features.md) のとおり
- 作るエージェントの許可: 素の状態では基本的に全て許可する状態で、利用者が設定をする
- Claude Code など他のエージェントと比べるかと、何で比べるかは、機能の品質を計測できる段階になってから決める

## 技術

- 言語は Python。端末から実行する。Python の版は 3.1 以上であればなんでもよく、Poetry で版を固定する（固定した版は `pyproject.toml` のとおり）
- 依存は極力小さくし、依存が発生した際に依存していることを分かりやすくする。実行するコードは標準ライブラリを基本にする
- コードの lint はサードパーティに依存してよい（それが最も有効であるため）。行える範囲での静的検査を行う（Python なら mypy などの型の検査も併用する）。細かい内容は追々詰める
- 実行環境とモデル: Ollama の公式アプリと、Qwen3.5-9B（基準）・gpt-oss-20b（推論の強さを試す用）

### モデルとの接続

- Ollama には、独自の API（`/api/chat`）で要求を送る。道具の呼び出し・ストリーミング・推論の段階（gpt-oss の low・medium・high）・JSON Schema による出力の指定を、全て使えるためである
- ハーネスの中の会話の形は、Claude の Messages API に揃える。会話を、本文・thinking・`tool_use`・`tool_result` の塊（content block）の並びとして持ち、送る直前に Ollama の独自の形へ変換する層を1つ置く。理由: 理解したい対象は Claude Code なので、中の形を揃えると見比べやすい。後で Anthropic 互換の口（`/v1/messages`）を足せば、同じ形で比べられる
- 比べた案: Anthropic 互換の口を直接呼ぶ（Ollama の互換は `tool_choice` を持たず、thinking は基本の形だけで、`budget_tokens` は効かない）／OpenAI 互換の口を呼ぶ（Claude Code とも Ollama の独自とも違う第三の形になる）
- SDK は使わず、標準ライブラリの HTTP（`urllib.request`。応答を1行ずつ読む）で書く。全てのコードを人が読むので、読む範囲の外の部品を減らす

### コードの置き方

- 実行するコードは、Python のパッケージ `local_coding_agent/` の下に置く。機能を作るたびに足し、先回りして作らない。細部（分け方・名前）はこのリポジトリで決めてよい

| 場所 | 中身 | 最初に要る機能 |
|---|---|---|
| `model/` | Ollama との接続と、会話の形の変換 | F-01 |
| `cli/` | REPL と、後の headless | F-01・F-21 |
| `trace/` | 走行の記録（要求と応答・トークン数・時間を JSONL へ） | F-01 |
| `context/` | system prompt・環境の知らせ・指示ファイル・要約 | F-02・F-11・F-12 |
| `loop/` | エージェントのループ | F-03 |
| `tools/` | 道具を1つ1ファイルで | F-03〜F-05 |
| `permissions/` | 確認・規則・モード | F-03・F-06 |
| `commands/`・`skills/` | slash commands と skills | F-07・F-08 |

- テストは `tests/` に置き、標準ライブラリの `unittest` で書く。モデルは、決めた台本どおりに返す偽物にする
- 試すための小さな課題（失敗するテストを1つ持つ小さなプロジェクトなど）と、通ったかを判定するコマンドを `tasks/` に置く
- 走行の記録は git に入れない（機械が出す記録なので）
- 1ファイルは 200 行程度、関数は 50 行までを目安にする。1機能の変更を、人が一度に読める大きさに保つため

### 持ち主が行うこと（リポジトリの外に入るので、Claude Code は行わない）

- Ollama の公式アプリを入れる
- Ollama のクラウドの機能を切る（`OLLAMA_NO_CLOUD=1`、または `~/.ollama/server.json` の `disable_ollama_cloud: true`）
- 文脈の長さを広げる（GPU のメモリが 24 GiB 未満の機械では、既定は 4k トークンで、エージェントには足りない。`OLLAMA_CONTEXT_LENGTH`）
- モデルを取り込む（`qwen3.5:9b` か MLX 用の `qwen3.5:9b-mlx`、と `gpt-oss:20b`。どちらのタグにするかは持ち主が決める）

## 上流のリポジトリとの役割分担と受け渡し

- 上流のリポジトリ（非公開）は、要件や目的など最上流の判断を行い、実装した結果や知見を回収して記録する。このリポジトリは、実装・実行・運用を行い、結果を `docs/outbox/` へ記録する
- 上流からこのリポジトリへ移すのは、要件・目的・上層のフィードバックだけである。それ以外（説明の文書・技術の説明・コード・設定）は、このリポジトリのセッションが書く
- 開発は、このリポジトリで起動した対話セッションで行う
- ファイルによるやりとりは全て `docs/inbox/`・`docs/outbox/` で行い、どちらも git に入れない。inbox に書くのは上流だけ、outbox に書くのはこのリポジトリだけである。どちらのファイルも消さない。inbox を処理したら、outbox の報告にそう書く
- 対話した方が良い場合は、SendMessage（Claude Code のセッションの間でやりとりする機能）でやりとりする

### inbox と outbox の書式

| 向き | ファイル名 | 中身 |
|---|---|---|
| 上流 → このリポジトリ | `docs/inbox/YYYY-MM-DD-NN-<題>.md` | 冒頭に種類（要件の変更・指示・問いへの答え・情報）・起点・求める返事 |
| このリポジトリ → 上流 | `docs/outbox/F-NN-<題>.md` | 機能ごとの記録 |
| このリポジトリ → 上流 | `docs/outbox/YYYY-MM-DD-NN-<題>.md` | 報告（inbox を処理した・課題・知見・上流への問い） |

- 処理した印: inbox のファイルを処理したら、outbox の報告に「inbox/<名前> を処理した」と書く
- 直し: outbox のファイルは、書いた後で直すときは追記にする（消さない）
- SendMessage: ①inbox に置いた・outbox に書いた、の知らせと、②その場で決めたい相談に使う。記録や要件の中身は SendMessage で渡さない。SendMessage で決まったことは、受けた側がファイルに書く
- 判断の分担: このリポジトリで人がその場で決めてよいのは、実装の細部（仕様の中身・名前・ファイルの分け方）である。目的・要件・機能の範囲・禁止事項を変えるときは、outbox の報告で上流に上げる

## 進め方と記録

- 機能をひとつずつ実装する。Claude Code が主に実装し、人がコードを読み、理解する。基本的に全てのコードを人が読む
- 機能ごとに、人が自分で書くか、Claude Code が書いて人が読むかを選べる。既定は Claude Code が書き、人が読む。人が自分で書きたい機能があれば、その機能は人が書く
- 1つの機能は「仕様を決める → Claude Code が実装する → 人が読む → 試す → 記録する」で進め、人が読み終えるまで次の機能に入らない。1機能の変更は、人が一度に読める大きさに分ける
- 機能がひとつ実装された段階でその機能を試し、結果を記録する。この記録は、最終的にはブログなどの形式で公開する想定である。公開できる文体である必要はないが、「ある機能をどのような要件・仕様で実装し、どうなったか」という、公開に必要な情報は記録しておく
- 機能ごとに1つ、outbox に記録を書く。後でブログにするときに書き足さずに済むよう、次の項目を持つ
  - 要件（何を作るか・なぜ）
  - 仕様（入出力・振る舞い・作らないこと）
  - 実装の要点（主なファイル・設計の選択と捨てた案・commit）
  - 試し方（課題・モデル・設定）
  - 結果（期待との差。失敗を含む）
  - 数値（応答までの時間・トークン数・課題を通せたか）
  - Claude Code との違い
  - 人が読んで分かったこと・分からなかったこと
  - 残った課題
- 記録の項目のうち「仕様」と「数値」は、`docs/features/f-NN-<機能名>/` の文書を指す
- 作業の進行管理・記録用のファイルを docs/ 以下に git に入れずに作り、現在の進行を記録する。常に現在の実装・進行の状況を更新する

### 1機能の進め方の細部

「仕様を決める → Claude Code が実装する → 人が読む → 試す → 記録する」を、次のように行う。上流は機能ごとに指示を送らない。機能の中の仕様は、このリポジトリで人と決める。

1. **仕様**: Claude Code が、`docs/features.md` の行から、その機能の仕様（入出力・振る舞い・作らないこと）を書き、人が承認する。このとき、人が自分で書くかを確かめる
2. **実装**: Claude Code がコードとテストを書く。テストは偽物のモデルで通す
3. **読む**: 人が全てのコードを読む。Claude Code は読む順の案内を付け、人の問いに答える。分からなかった点は記録に残す
4. **試す**: 人が、実物のモデルで `tasks/` の課題に掛ける（下の「動作検証で、実物のモデルで走らせる扱い」）
5. **記録**: outbox に機能の記録を書き、コードを commit する。人が読んで push する

### 動作検証で、実物のモデルで走らせる扱い

作るエージェントは素の状態で全て許可するので、作るエージェントが起こすコマンドは Claude Code の許可の判定を通らない。

- **許可の機能（F-06）ができるまでは、実物のモデルで走らせるのは人だけである**。Claude Code は、偽物のモデルを使うテストまでを行う。今の sandbox が手元の Ollama に届かない設定でも、これで足りる
- **F-06 ができたら、Claude Code も実物のモデルで走らせてよい。ただし、作るエージェントに、Claude Code が守る運用の要件（削除の禁止・リポジトリ外の禁止・秘匿情報の禁止など）にあたる許可の規則を設定して走らせる**。そのとき、手元の Ollama だけに届くよう設定を書き起こし直す（`derive-settings`）。持ち主の利用者の設定を変える必要が出たら、上流に上げる
- 人が見ていないところで走らせる（課題の繰り返しなど）ときに、OS のサンドボックスを重ねるかは、そのときに上流が持ち主に問う

### 試し方と数値

- 課題は `tasks/` に置き、通ったかをコマンドの終了コードで判定する
- 数値（応答までの時間・トークン数・課題を通せたか）は、走行の記録（F-01）から取る
- 比べ方（Claude Code など他のエージェントと比べるか）は、要件のとおり後で決める

### 記録の書き方

- outbox に、機能ごとに1つ `docs/outbox/F-NN-<題>.md` を書く
- 項目は上の9項目に、**読む順の案内**（人が読んだ順と、その順にした理由）を足す
- 記録の雛形をこのリポジトリに置く。置き場と形はこのリポジトリで決めてよい（雛形は記録を書く手順なので、docs/ の説明の文書ではない）

## 公開と文書

- このリポジトリは公開するものである。docs/ の想定読者は、コーディングエージェントの仕組みを知らないソフトウェアエンジニアである
- 利用する技術や作成する機能の概要を docs/ へ入れる
- docs/ には静的な情報を置き、経緯などは入れない。リポジトリが公開された状態について書く
- docs/technologies/ には、一般的なソフトウェアエンジニアが知っている情報を書かない
- docs/ と docs/technologies/ の記載の規則は、skill か rule として設定する
- 本リポジトリは機能ごとに作っていくため、機能ごとにディレクトリをつくり、実装前の仕様、実装後に実際に実装された仕様、（あれば）計測結果、等の、その機能に関連する文書をそのディレクトリへ入れる。機能ディレクトリは `docs/features/` 以下へ作成する。機能ディレクトリ群が自然に名前でソートされるように、命名は `f-n-{機能名}` とする（番号は2桁で、`f-01-<機能名>` の形）
- 実装前の仕様と計測の結果は、その時点のものとして直さずに残す。「静的な情報を置き、経緯などは入れない」は、この2つには当てない
- プロジェクトのセットアップ方法、起動、使用方法を README.md へ記載する。また、機能を追加するごとに README.md の内容を更新していく
- 個々のプロジェクトの要件の置き場は docs/ の下で、公開してよい
- push は持ち主が行う

## 運用の要件（このリポジトリだけではない一般的な要件）

Claude Code（このリポジトリで開発するセッション）が守る要件である。

- **ファイル削除系の操作は禁止する**。Claude Code が行う削除（`rm`・`git rm`・`git clean`・元の名前が消える `mv`・未コミットの変更を捨てる `git checkout`/`git restore`/`git reset --hard` など）が対象で、作るプログラムが自分の中で行う削除（テストの一時ファイルの片付けなど）は対象にしない。削除が要るときは人に頼む
- **リポジトリ外のリソースに対する操作は禁止する**
  - リポジトリ外のファイルの編集は禁止する。リポジトリ外のファイルを読むことも許さない
  - 道具の導入とモデルの取り込みは、リポジトリ内にしか影響しないものであれば行ってよい（例: 仮想環境はリポジトリの中に作る。リポジトリの外に入るもの、たとえば `~/.local` への道具の導入や `~/.ollama` へのモデルの取り込みは、人が行う）。一時ファイルは、リポジトリの中の git に入れない場所に置く
  - git の remote リポジトリへの操作（追加・編集・削除・push など）は、設定上は ask（実行の前に人に確かめる）とするが、運用上はエージェント側では基本行わない。読むだけの操作（`git fetch`・`git pull` など）は allow（確かめずに行う）とする
  - デプロイや、外部へ何らかの影響を及ぼす操作は禁止する（GitHub などのサービスを書き換える操作・外部への送信など）。インターネットから読むだけの操作（文書を確かめるなど）と、手元の Ollama を呼ぶことは許す
  - 環境変数や秘匿情報の読み取りは禁止する（`env`・`printenv`・`echo $…`・`.env` などの秘匿のファイル・`~/.ssh`・`~/.aws`・キーチェーンなど）。作るプログラムが実行時に設定を環境変数から読むことは対象にしない
- **強制のための書き方**: それらの許可・禁止を Claude Code の設定で強制できるようにするために、特に shell コマンドは、必要ない限り間接的な呼び出しを避ける（`cd ... && xxx` や `git -c xxx` など）。また、Claude Code の標準機能を優先して利用する（ファイルの読み込みはツールを使い、shell で行わない、など）。Claude Code の仕様上、コマンドの一致単位でしか禁止できないが、実際に禁止したいのは操作であるので、回避できるとしても行わない（これは行える範囲で）

## 運用の要件（このリポジトリ固有）

- 人の理解を進めるのが大目的である。機械が自律的に行うべき作業は小さく、他のプロジェクトと比べて、人と相談して進める運用に寄ってよい
- 機械が自律的に行う作業は、機能の実装（テストを書くこと・手元の commit を含む）と動作検証、docs/ の記載、outbox への記録である。それ以外（仕様の決定・CLAUDE.md や rule や設定の変更・依存や道具の導入）は、人と相談して進める

## 要件から設定を書き起こす

- CLAUDE.md や Claude Code の設定は、具体的に書きたい内容があるわけではない。どのような設定を行うべきかの要件（この文書の上の節）だけがあり、それを、このリポジトリの内容と、その時の最新の設定方法により、具体的な設定に書き起こす
- 要件から、現在のリポジトリの状態に合わせて設定や lint のルールを書き起こす指示書を、リポジトリに置く（`.claude/skills/derive-settings/`）。要件を守っているかを確かめる lint は、将来入れる

### 書き起こしの指示書の要件

1. 入力は docs/ の要件である
2. 毎回、その時の最新の Claude Code の設定方法を公式の文書で確かめる（設定の方法は版で変わる）。確かめた日と、Claude Code の版を残す
3. 今のリポジトリの状態（言語・道具・ディレクトリ）を読む
4. 要件ごとに、何で強制するか（permissions の allow・ask・deny、hook、sandbox、rule、CLAUDE.md の指示、lint と静的検査）と、設定では止められない部分を、対応表にする
5. 書き起こしたあと、禁止のはずの操作が止まるかを確かめる。止まらないものは対応表に書く
6. 書き起こした CLAUDE.md・rule・設定の変更と、道具の導入は、持ち主の承認を得てから行う
7. 呼ぶ時機: 要件が変わったとき・Claude Code の版が上がったとき・リポジトリの状態が変わったとき（道具を足したなど）
